# Threat model

## Assets

- Room configuration, current deadline, assignee, and event history.
- Room access keys and the optional server-wide room-creation token.
- Availability and integrity of the SQLite file.
- Household member names entered as actor labels.

## Trust boundaries

The Python process and its SQLite file are trusted. Browsers holding a room key are authorized for
that complete room. Other devices on the network, reverse proxies, imported archives, URLs, and
all client-provided names and JSON are untrusted.

## Defenses in v0.1.0

- 192-bit URL-safe room keys generated by the operating-system CSPRNG.
- Only key digests persisted; constant-time digest comparison.
- Fixed body, name, participant, wait, and archive size limits.
- Parameterized SQL, immutable domain records, and transactional version checks.
- Fixed packaged-static allowlist; no path-derived filesystem reads.
- Archive verification without extraction; exact member set and SHA-256 manifest.
- Same-origin API, no cookies, no CDN, restrictive content security policy, and no dynamic HTML
  insertion for user values.
- Access keys kept in URL fragments rather than query strings; exports omit keys.
- Optional server-wide token to prevent arbitrary room creation.

## Accepted risks and limits

- A private join link is a bearer capability. Anyone who receives it has full room access.
- There is no key rotation, member revocation, per-action authorization, or verified identity in
  v0.1.0. Actor names are claims.
- Room existence and key guesses have distinct internal paths; rate limiting is expected at the
  reverse proxy for internet deployments.
- Plain HTTP does not protect authorization headers from network observers.
- Browser background throttling may delay display, sounds, notifications, or long-poll reconnects.
- A single process is the supported topology. Multiple processes will persist safely through
  SQLite but will not promptly wake each other's waiting clients.
- A host administrator or filesystem attacker can read or alter all state.
- SHA-256 verifies archive integrity against its included manifest, not publisher authenticity.
  Verify release assets against the GitHub Release checksums over authenticated HTTPS.

## Deployment checklist

1. Keep DutyBell on a trusted LAN, or terminate current TLS at a maintained reverse proxy.
2. Set a long random `DUTYBELL_CREATE_TOKEN` for any shared or public host.
3. Limit request rates and connection counts at the proxy.
4. Restrict filesystem permissions on the data directory and backups.
5. Back up with SQLite's backup API and test restoration.
6. Patch Python, container base images, and the reverse proxy regularly.
7. Treat leaked links as compromised and replace their rooms.
8. Never use DutyBell as the only alarm for health, safety, or material-loss scenarios.
